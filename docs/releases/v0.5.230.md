# GPTWork v0.5.230 — Accurate forwarded model and GPT-5.6 Sol identity

## v0.5.229 real-machine evidence

The user chose official GPT-5.6 Sol (the official Chat composer shows "5.6 高") and observed false floating "GPT 5.6 · 不符合锁定". The page UI and actual request use two different labels: Picker A GPT-5.6 Sol and request protocol `gpt-5-6-thinking` (normalized `gpt-5.6-thinking`). Treat these as one **lock family** while preserving the raw request/response transport identities for diagnostics.

A separate GPT-6-only test with request `15316.5513` exposed the main bug. The sole terminal private Fetch authority reported a successful `Fetch.continueRequest` POST rewrite from `gpt-5-6-thinking` to `gpt-6` at 07:40:48 UTC. The later `Network.requestWillBeSent` callback for the **same** request ID reported its pre-rewrite `gpt-5.6-thinking` observation. Background mistakenly overwrote `lastRequest.model` with that observation and floating UI preferred it, displaying GPT 5.6 as "locked" when Fetch had explicitly forwarded GPT 6.

## Fix

- Add one pure request-evidence correlation helper that only accepts matching formal Network and successful Fetch IDs, not unrelated or failed callbacks. Retain the original observed model as `observedModel`; set `lastRequest.model` to the successfully forwarded `modelAfter`. Support both event arrival orders and preserve per-turn immutable policies and raw diagnostics.
- Align the presentation, official Picker A alias parsing, historical model matching, policy and the sole private Rust request authority for `GPT-5.6 Sol` / `gpt-5-6-thinking`. Keep the raw protocol model unchanged; GPT-6 and non-Sol tiers remain distinct.
- Do not infer a served backend model from the selected UI model or the outgoing request. Response confirmation still requires attributable backend response metadata.
- Add regression tests replaying actual v0.5.229 request IDs and model values, including failed/unrelated callbacks, GPT-6-only mismatch, and GPT-5.6 Sol family.
