# GPTWork v0.5.224 — model-lock authority and truthful served response

## Root cause

The outgoing `rewriteConversationPostData` trusted every *known* page-selected model even if it was **not present in the explicit lock allow-list**. For example, a ChatGPT picker showing GPT-5.6 Sol while only GPT-6 is locked could forward GPT-5.6 Sol instead of applying the lock. This mixed two distinct authorities: passive page observations and request authorization.

The floating catalog and popup also had response display fallbacks that could prefer the policy verifier over an already observed real network `served/resolved/used` model. The catalog exposed direct model observations only in the no-lock case; in locked/mismatched states it relied on the verifier, which may be unavailable or reject the model.

## Changes

- The **allow-list** is authoritative for the final intercepted request: preserve a page-selected model only when it is both known and explicitly allowed; otherwise rewrite to the configured locked target. Explicit discovery `forceModel` retains its own authority.
- Keep ChatGPT's official picker and reasoning controls read-only during ordinary Chat. The UI's page selection may differ from the outgoing locked model by design.
- Show real response metadata **independently of request equality and lock-policy verdict**, including a mismatched `gpt-6-thinking`. Separate three facts: page selected, final sent, actual served; label actual response and lock rewrite explicitly.
- An attributable served response is displayed even when verification verdict is `mismatch` or unavailable. It is **never** claimed verified without an actual verification pass; reject conflicting or unrelated response metadata.
- Keep protocol model IDs such as `gpt-6-thinking` distinct from UI/business IDs like `gpt-6` unless an explicit tested mapping proves equivalence.

## Regression coverage

- Known-but-disallowed page models cannot bypass GPT-6-only lock.
- Allowed page selection is preserved, and discovery force overrides independently.
- `page GPT-5.6 Sol / request GPT-6 / response GPT-6 Thinking` displays all three real identities, with response mismatch separately.
- Stale, conflict-marked, non-authoritative response metadata never becomes a current served model.
- No automatic page-picker alignment outside discovery.

## Remaining risk

Real ChatGPT backend acceptance of a rewritten transport ID still requires a user-reproduced request/response in Chrome/Edge; actual served-model fields cannot be manufactured. CI passing alone is not proof of server model selection.
