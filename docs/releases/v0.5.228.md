# GPTWork v0.5.228 — Preserve multi-model lock policy when Picker A is unknown

## Reproduction from v0.5.227

On 2026-10-15, the normal Chat composer displayed only a reasoning-only High pill while the saved Model Lock selected both GPT-5.6 Sol and GPT-6. The official ChatGPT request used `gpt-6-thinking` and `high`, but its frozen per-turn policy snapshot contained only `gpt-5.6-sol`. The UI therefore showed an apparent lock mismatch despite the user's explicitly allowed GPT-6 choice.

A separate `request_lock_checked` diagnostic contained neither Fetch nor Network request IDs and had `reason=no_locked_model`. It was not proof about the formal ChatGPT request. A real response model can be observed without enough metadata for final policy verification; avoid claiming an unverified backend identity.

## Fix

- Keep **all** explicitly selected Model Lock families when official Picker A model evidence is unavailable. Do not silently choose the first allowed model because the composer shows only High.
- Keep precise Picker A narrowing when a checked, permitted model is observed. Reuse the existing policy family's GPT-6 / gpt-6-thinking equivalence; do not add any secondary lock authority.
- Relabel no-ID request observations as diagnostic, not formal lock checks.
- Distinguish concrete model/reasoning policy mismatch from truly incomplete backend response metadata rather than always using `response_metadata_incomplete`.
- Update the legacy High-only test and add source-executed regression cases for two allowed models, checked Picker A selection, GPT-6 Thinking and incomplete evidence.

## Validation

Extension and packaging CI must succeed for this exact release source. The user's real browser must still verify Picker A and actual served model using the request/response evidence after installing this release. No model identity is inferred solely from the reasoning-only High pill.
