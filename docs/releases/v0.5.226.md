# GPTWork v0.5.226 — GPT label separator equivalence and lock-verdict diagnostics

## User reproduction

The v0.5.225 official Picker A UI marked GPT-6 selected while the floating panel displayed GPT-6 with a “不符合锁定” warning; a later capture showed GPT 6 Sol selected, GPT 6 locked and direct GPT 6 Thinking response, and an in-page "Confirmed response model mismatches the lock policy" guard.

In the uploaded runtime log, tab 124173918 had a formal network request and response model `gpt-6-thinking` (high). At 04:38:48Z, its response was classified `model_not_allowed`. The log did not include the evaluated lock-list snapshot, so the record cannot prove this mismatch was caused *only* by typography; differing policy/feature state is another possibility.

## Fixes

- An explicit numeric GPT label written with spaces or hyphens canonicalizes to the same **identity**, e.g. `GPT 6` / `GPT-6`, `GPT 5.6` / `GPT-5.6`, `GPT 6 Sol` / `GPT-6 Sol`, `GPT 6 Thinking` / `GPT-6 Thinking`.
- Apply consistent canonicalization in extension model policy, floating status, persisted response history and native Rust policy/model verification. Preserve the exact wire transport string in request and response diagnostics.
- Keep the intentional v0.5.225 lock-family rule: a numeric base GPT version equals its exact `-thinking` sibling **for lock policy**, but `-sol` is a distinct model tier. Never treat GPT-6 Sol as GPT-6 Thinking.
- Record `lockedModelsAtInterception` and feature state, `lockedModelsAtRequest`, and `lockedModelsAtVerification` with the `policySource` for each response verdict, so mismatches can be traced to their actual authority rather than guessed from the UI.
- Guard regression ensures a stale model-not-allowed verdict with real GPT-6 Thinking cannot block when the current locked display ID is GPT 6; a true Sol mismatch remains blocked by strict policy.

## Remaining checks

CI and real Chrome verification are still necessary. The previous runtime also showed no-Fetch-ID `no_locked_model` events and SSE aborted/closed transport. Those are separate observations and should not be represented as solved by display-name normalization.
