# GPTWork v0.5.231 — Administrator enablement controls model-lock availability

## Existing behavior

On the admin **共享模型目录** page, **保存** previously saved all three row fields: display label, Picker (A/B), and the existing enabled checkbox. If the update changed values, the server increased the catalog generation. However, the client model list also required one account's 4/4 discovery/request/native-response/Chat-lock verification gates; simply enabling the model did not make it selectable. Independent availability/tab runtime code could also repopulate models that the administrator had disabled.

## New behavior

- Each catalog row has an explicit **启用 / 停用** action. Clicking it immediately calls the authenticated admin PUT API with only `{model,enabled}`; its enabled state and status text are updated after successful confirmation. **保存** now only saves edited name and Picker and does not change enablement.
- The server publishes only rows with `enabled=1` as client lock choices. It retains evidence counters and 4/4 `clientEligible` as diagnostic information; incomplete verification is never represented as proven execution.
- The client synchronizes the new generation, filters the server catalog strictly by its enabled flag, and removes disabled models from both the saved per-turn model lock policy and the independent selection cache. The popup editor and full options lock list show enabled models only.
- The availability auto-selection and tab-specific feature runtime can no longer silently re-add administratively disabled models or fall back to a disabled Sol model.
- Automatic discovery of existing models continues to preserve historical enabled states; the admin explicitly changes them with **启用 / 停用**. Discovery evidence is not deleted when a model is disabled.

## Validation

Require admin UI/server policy tests, extension policy regressions, native/private-core checks, and full Windows/Linux packaging CI. The exact release assets must be generated from the successful main commit.

## Operational note

The enablement change takes effect on clients when their next catalog-generation synchronization succeeds. Enabled means the model can be selected for lock; it does not guarantee a successful backend served-model response. Disabled models can still be observed in diagnostic discovery evidence but must not appear as selectable lock targets.
