# GPTWork v0.5.233 — Safe SQLite WAL/SHM updates

## Incident addressed

A deployed License Server remained at v0.5.200 because the one-click updater reached 95% and rolled back after Node SQLite failed at `server.mjs:48` with extended SQLite error `4874` (`SQLITE_IOERR_SHMSIZE`). The updater used root to open the live SQLite DB for app-settings snapshots, backups, and verification, creating a risk of root-owned `-wal` / `-shm` sidecars that the unprivileged service cannot resize.

This is a plausible, code-confirmed failure mechanism, **not** proof that every 4874 error is permissions-related: full disks, read-only mounts, inode exhaustion, and underlying I/O errors also require diagnosis.

## Changes

- Execute **every updater SQLite connection** (settings snapshot, SQLite online backup, settings verification and recovery) as the configured service user/group via `runuser`, not as root.
- Ensure the private backup directory is writable by that runtime identity; retain mode `0700` for backups.
- Before deployment and again before/after backup, verify SQLite access and directory/WAL/SHM writability as the actual runtime identity. Abort **before git reset or service restart** on failure.
- Include SQLite file ownership/modes, filesystem free bytes/inodes and mount information in the protected updater log when a check or health verification fails.
- After rollback, check service restart and HTTP health rather than silently treating an unsuccessful rollback as recovered.
- Do **not** delete or truncate the database, `-wal` or `-shm`, and do not silently change existing SQLite file ownership.
- Add regression tests that execute the WAL preflight and verify all five SQLite operations use the service identity.

## Upgrade caveat for installations still running v0.5.200

The one-click updater is executed from the **currently deployed checkout**. A failed deployment rolls that checkout back, so this corrected script cannot protect the *first* attempt until the old WAL/SHM permissions or filesystem fault has been repaired. Before retrying, an administrator should inspect the live service's effective `GPTLOCK_LICENSE_DB` path, database and `-wal`/`-shm` ownership, directory permissions, free disk space/inodes and mount status. If files are incorrectly root-owned, back up the database consistently, stop the service, and repair ownership only on the confirmed database and sidecars; never remove WAL/SHM. Recheck the service and then use one-click update to deploy this release.

The License Server control panel version remains `0.2.0`; the GPTWork product version advances to `0.5.233`.
