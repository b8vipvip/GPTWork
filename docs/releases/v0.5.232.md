# GPTWork v0.5.232 — Editable administrative verification status

## User-facing behavior

The administrator's **共享模型目录** now has a separate **验证状态** column with a per-model selector and **更新状态** action:

- **自动判断** (default): status derives from actual same-account 4/4 discovery/request/native-response/Chat-lock evidence.
- **人工已验证**: explicitly mark as administratively verified, without forging successful request/response/Chat-lock evidence.
- **人工待验证**: explicitly mark as pending verification.
- **人工验证失败**: explicitly mark as failed verification.

The selector shows whether the displayed status is **人工标记** or **自动证据**. When marking verified manually, a confirmation warns that real proof is unchanged.

The existing **启用 / 停用** action remains the *only* server authority for whether a model is listed as a client lock choice (v0.5.231 behavior). The **保存** button continues to update only label and Picker. Manual verification status is an annotation, not an additional model-choice gate, not a model-rewrite instruction, and not an assertion of actual served-model response.

## Implementation

- SQLite catalog and recycle-bin schemas gain `verification_status_override` (default `auto`), with migrations for existing databases and strict allowed values.
- Authenticated admin PUT accepts `verificationStatusOverride` independently of label/Picker/enabled. Invalid values are rejected with HTTP 400; unchanged updates do not bump generation.
- Status changes are transactionally persisted and audited; changes bump the shared catalog generation. Discovery and evidence updates never overwrite the administrator's status override.
- Deletion/restoration roundtrips preserve status overrides and account verification evidence.
- Admin and client catalog expose effective verification status, source, and raw override. Extension UI displays manual vs automatic status and separately displays the actual 4/4 evidence.
- No fabricated request confirmations, native responses, Chat-lock confirmations or per-account verification ledger changes.
- Correct the remaining local availability veto: when a synchronized administrator catalog is present, its enabled models remain selectable even if account-local automatic availability probing reports a negative result. The UI warns about the negative probe without disabling the checkbox. Disabled models are still removed, and legacy local availability handling remains intact when no server catalog exists.

## Validation

Automated server integration tests cover admin status updates, invalid input, no-op generations, frontend catalog enabled-only exposure, real-evidence isolation, and trash restore. Extension and server regression suites, private-core boundary checks, Windows/Linux build CI, exact-main-SHA Release gating are required before publishing.
