# GPTWork v0.5.250

## v0.5.249 真机证据与新问题

v0.5.249 的普通请求 SSE 对照记录 **已正常生成**。在同一个已存在 ChatGPT 会话里：
- 普通 `gpt-6-thinking` 正式请求 `15564.1461` 与 `15564.1596` 均获 HTTP 200，之后被 Chrome `canceled=true/net::ERR_ABORTED`；SSE `[DONE]` 与某条助手消息的 `finished_successfully` 信号均被观察到。
- Astra 调试请求 `15564.1490` 与 `15564.1634` 均被改写转发 `gpt-6-astra-wm`，HTTP 200，之后 `net::ERR_ABORTED`；SSE `[DONE]` 已出现，但状态只观察到 `in_progress`，没有 `finished_successfully`，页面回复观察均约 110 秒后超时。响应 `resolved_model_slug=gpt-6` 是 GPT-6 家族级，`default_model_slug=gpt-6-astra` 不是权威执行模型。
- 普通 SSE 汇总同时出现 `sseAssistantFinalSeen=true` 和 `sseAssistantStatus=in_progress`，因为两字段含义不同：前者是**任一**助手消息曾 `finished_successfully`，后者是**最后**一个观察到的助手状态。不同 SSE 消息的状态被显示成好像属于同一助手消息，容易误判全轮成功。

## 变更

- 共享同一个只读 SSE 分类器，新增独立的 `sseAssistantEndTurnSeen`：仅当同一条助手消息明确 `status=finished_successfully` **且** `end_turn=true` 才记为真。该信号仍不能覆盖 Chrome `loadingFailed`，也不能直接证明 Astra 实际运行。
- 新增 `sseAssistantStatusSequence`：最多 16 次状态变化，仅保存允许枚举值（`in_progress` / `finished_successfully` 等），**不保留任何消息 ID、回复正文、用户文本或原始 SSE**。状态序列可以横跨多个助手消息，不应视为同一消息的进度。
- UI 分别显示任一助手消息完成信号、明确的助手整轮 `end_turn` 信号、最后观察到的助手状态，以及脱敏的跨消息状态变化。
- 正常请求诊断与 Astra 诊断均导出上述字段；未捕获到 SSE 正文时新字段为 `null`（未知），不得误报为否。
- 增加回归测试覆盖“中间消息完成但最后状态仍为进行中”“真实 `end_turn` 信号”“网络已被取消但 SSE 有整轮信号”“隐私边界”。

## 实机验证

在相同已有会话中，先手动发送普通 GPT-6 请求，再通过 GPTWork 调试工具发起固定 Astra 请求。上传 Astra 调试 JSON 和运行时 JSONL，对照普通请求与 Astra 的 `sseAssistantEndTurnSeen`、`sseAssistantStatusSequence`、`[DONE]`、Chrome 网络取消与页面可见回复。

**仍未解决/验证：** 两类请求为何都出现 `net::ERR_ABORTED`，以及 Astra 请求是否由服务端实际以 Astra 模型执行。模型请求改写、HTTP 200 或 SSE `[DONE]` 均不足以证明后者；若要定位取消源，应增加独立的 GPTWork 禁用/启用实机对照。
