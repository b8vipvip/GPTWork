# GPTWork v0.5.229 — Restore private request model-lock enforcement

## v0.5.228 user evidence (2026-10-15)

The actual normal-Chat POST `15316.4697` used `gpt-6-thinking`, `high`; its immutable request policy contained `['gpt-5.6-sol', 'gpt-6']`, and the attributable SSE response contained 25 identical `resolved_model_slug: gpt-6-thinking` / `thinking_effort: high` observations. The model verifier returned `verified` with `decision=allow`. This proves the response identity and fixes the former false policy mismatch; it does not prove active request mutation was applied.

A review of the actual private request routing exposed a separate enforcement defect: `private-request-hook.js` called `this.configuration()` without `tabId`. The private engine thus received an empty model lock list (and reported `no_locked_model`) even while the public request/response policy had two allowed models. The callback also omitted the formal Fetch request ID, leaving only incidental uncorrelated observations. Hundreds of non-conversation GET/prepare requests flooded the observer log.

## Changes

- Pass the actual tabId to the *single* private request authority's configuration reader. Model decisions now use the same tab-scoped explicit policy as the request and response verifier.
- Preserve the exact permitted outgoing model and protocol ID, including official `gpt-6-thinking` under the selected `gpt-6` family; do not overwrite valid selections with the strongest unrelated allowed fallback. Rewrite only disallowed models to an authorized target.
- Make the sole terminal private request callback carry real Fetch and Network request IDs for formal requests.
- Keep unrelated history, prepare and conversation-list requests flowing unmodified, without emitting fake lock observations or overwriting lastRewrite.
- Add a source-executed mock routing regression and Rust engine policy tests for allowed Sol, allowed GPT-6 Thinking, disallowed fallback, and separate non-equivalent tiers.

## Release gates

Require full extension policy tests, Private Core Rust tests, Linux and Windows builds, and exact-SHA main CI to succeed before official release. Live confirmation after upgrade should show a formal `request_lock_checked` or `request_lock_rewritten` with a Fetch ID and matching request/response model evidence. A `verified` response alone must not be treated as proof that request mutation worked.

The single v0.5.228 SSE response was captured from an `initial_conversation_aborted` (`net::ERR_ABORTED`) stream. Its served-model metadata was valid, but it did not prove normal response-stream completion.
